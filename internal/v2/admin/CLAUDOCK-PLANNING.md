# Installed Claudock planning

The installed factory measures the exact protected Claude Code executable with
`--version` and `auth status --json`. Each credential mode uses synthetic input
and a fresh private home, with updater and nonessential traffic disabled. The
output must select the expected first-party API-key or OAuth-token method.
Both enrolled executable identities are checked before and after measurement;
a cached result still requires a fresh hash/enrollment check. No login or model
command is invoked. This is credential-selection evidence, not provider
authentication, a successful model request or subscription-refresh evidence.
The exact version/status output and both executable pins are retained in private
compatibility measurements. Output containing the synthetic input is refused
before retention; no credential value becomes an evidence field.

The event service never traverses the lane-owned home. Its `PlanHome` binding
calls the helper credential worker with the exact service-retained RunnerRequest,
current planning claim and opaque allocation/home IDs. The service adapter
reloads the protected request bytes, original reservation, current authority and
storage binding. The helper independently correlates its allocation journal,
boot, UID/GID, root ID, generation, owner, mode and device/inode. Missing,
foreign, collecting, replaced or nonquiescent storage refuses. Paths come only
from that helper journal, never from a lane or public request.

Before planning succeeds, a closed probe executes the installed fixed bootstrap
under the actual allocated lane UID, cgroup and private namespaces. It receives
only the enrolled immutable runtime mounts, no credential or lane storage, and
its release pipe is never opened. The bootstrap establishes umask 077 and reads
it back from the kernel. The helper independently reads the actual pinned
bootstrap process's kernel umask, retains the measurement with its artifact,
boot and exact reservation/input binding, and collects the probe. The actual
credential gate repeats the bootstrap measurement and rechecks the live process
immediately before delivering credential descriptors. No event-service umask
change or caller-supplied constant substitutes for that observation.

The root helper's credential worker stays within the shipped helper unit's
existing writable mounts. It initializes only the materializer's empty vendor
skeleton; an unrecorded populated or partial home is preserved and refused.
Generated entries retain the lane UID/GID and private modes. Home records remain
root-owned, mode 0700, under the helper state directory, outside every lane
mount. The worker runs the adapter's existing owned-entry/generated-file audit,
conversation checks and atomic binding/seal transaction and retains ordinary
tool findings privately. Changes to the same reservation's inputs and a foreign
start reservation still refuse.

Before a real Claudock gate starts, the helper opens the generated settings and
registry through their verified identities, compares their bytes with protected
digests, and mounts the actual files read-only over the lane home. The native
canary verifies chmod/write refusal in that namespace while ordinary home data
remains writable and protected records remain absent. The root canary starts
its helper-side test under umask 022, so inherited unit defaults cannot stand in
for bootstrap establishment.

Helper/API credential modes and native Darwin remain unavailable. Usage,
whole-run refusal coverage, provider authentication and automatic profile-swap
acceptance remain separate gates; credential selection does not enable them.
The installed fake-key lifecycle harness must still exercise the actual release
and vendor together. Its vendor authentication refusal is expected, and it must
retain its credential-persistence and cleanup observations.
