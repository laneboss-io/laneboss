# Item 5 implementation and remaining gates

Item 5 installed acceptance remains incomplete. Confined org rendering and the
protected installed controller/fixture-clock producer are still required. A
passing package run, native filesystem canary or software authenticator does
not establish an owner-in-person approval.

The store now joins proposals and approvals to the exact source snapshot,
generation comparisons, committed objects, requester launch, event and reply.
An absent proposal/approval event refuses atomically. The store assigns service
event provenance only after those checks. An applied event additionally needs
the private completion capability created by independent canonical readback.

Apply retains its original reservation, one consumed approval, immutable
publication inputs, effect and deferred reply binding. Pending replay reuses
that operation without consuming authority again. Final receipt/reply rows are
inserted once at completion; their immutable triggers are preserved. Restart
verification checks pending and completed publication joins.

Authorization captures and compares the current L6 life revision. After that
commit, the durable org operation is fenced by its consumed exact-change
approval and original effect, independently of the caller's later process
lifetime. `store.checkEffectFence` contains the narrow `ApplyChange` hook into
`orgApplyFence`; it leaves other lifecycle effect fences in place.

The Linux publisher creates a complete immutable generation below the state
directory's `org/generations/gen-OPERATION/tree`, records a durable sibling
`marker.json`, then atomically swaps `org/current`. Every source and derived
file is read from its actual committed object and independently checked on
disk, including modes, unexpected paths, symlinks and hard links. Publication
and readback do not hold the SQLite writer transaction. The publication lock
fences claim replacement during filesystem work. Generation one can begin from
the already administrator-approved object inventory; later generations require
their actual prior canonical pointer and marker.

Only the original live effect claim can complete publication. Success requires
the actual pointer, complete filesystem inventory and exact marker/receipt.
Failure requires independently measuring that the approved canonical base
remains unchanged. An uncertain outcome remains pending for reconciliation.
Completion seals the original deferred request and keeps its exact final reply
for replay. Org source/policy reads and new org/launch dispatch wait while the
generation gate is pending.

Canonical bytes do not implement an authoritative policy, channel, grant,
configuration or decision projection. Round 2 adds one bounded compiler:
`policy.RebindOrgSources` advances the provenance of unchanged approved policy
sources. It validates the original policy hash, exact source identity, bytes,
mode, kind and revision against both inventories, then advances the independent
policy generation and recomputes its content hash. Defining rule and guidance
references move with the source list. Historical policy and launch/grant records
retain their original bytes. New source files have Kind `source`, and new
generated files have Kind `file`, matching the shared inventory contract.

The original policy input and its deterministic compiled result are retained
with `org_apply`. Publication and measured completion compare them again;
completion writes policy and org heads atomically. Restart verification
recompiles the retained inputs, requires their approved policy history and
checks the current policy against the actual publication phase. A missing
policy for an enrolled policy source refuses before an effect is queued.
The retained compiler input also joins the original request's policy-generation
stamp at reservation, claim, publication, completion and verification. The final
receipt retains that original generation even after the policy head advances.

Changed authoritative source kinds remain blocked. Channel references,
including unchanged channel sources, also remain blocked until their compiler
exists. Policies containing skips or capture-refusal approval cannot use the
unchanged-source compiler: those authorities require explicit renewed semantic
approval. Parsing changed policy/config/channel/grant/decision content is still
open, as is native confined rendering. The component policy fixture supplies
an already approved baseline and retained generated bytes; it does not claim
either missing native producer or an installed owner ceremony.

Verified simulated presence is preserved through approval construction, the
original operation, publication marker, application and final deferred reply.
The harness accumulates observed marks and reports `presence=simulated` and
`human_approval=not_proven`. Untagged production builds retain their existing
software-authenticator refusal. The tagged identity tests exercise real
software signatures; they do not prove physical presence.

service outbox selects fresh publication on the first claim and reconciliation

opened staged sources, retained derived bytes and full independent rerender
comparison. Its current explicit refusal is preserved. The existing generic
worker bootstrap supports materialization and archive; a render label alone
does not install a native render worker or its authenticated result channel.

Enroll the fixed CLI/write jobs under actual L6/L5 actors and supply the
protected controller, injected fixture Clock, disposable datasets and pinned
UI helpers required by `README.md`. The CLI canary now consumes exactly the
sealed binding and O_PATH socket projections, retaining only those descriptors
at their original numbers for its subprocess. It does not accept a copied
regular lane-binding file or promote a worker UID to an L6 actor.

The harness exits 69 with retained typed `prerequisite-wait.json` evidence when
the controller or owner confirmation helper is unavailable. That result is an
unreached failure/wait in the frozen result contract, never a passed ceremony.
The owner must review the exact source plus derived package and supply fresh
operation-bound security-key/PIN/biometric confirmation. Same-connection human
read confirmation, physical browser gestures, root installation and live
authentication remain owner/installer steps; none was recorded as performed.
