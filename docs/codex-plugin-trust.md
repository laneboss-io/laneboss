Codex lanes receive invocation-local hook trust only after configured sources are vetted and plugins are disabled for that invocation. Prepare adds --disable plugins next to the trust bypass, and the exact binary's features list must report hooks true and plugins false under the lane's flags. Revet requires the disabling flag again before execution. The bundled acceptance adapter uses the same plugin-off flags and feature check.

The trust scanner checks the plugins table in instance and repository TOML, decoded preference TOML, and recursively nested structured values. Empty plugin tables and entries explicitly disabled with enabled=false are allowed. Enabled entries and entries whose enablement cannot be determined are refused. Plugin configuration overrides and plugin-enabling feature flags are refused. System and managed configuration sources retain the existing fail-closed layer check.

A marketplace clone in a vendor runtime directory does not establish whether a plugin is enabled. Org inspection excludes that opaque runtime using the renderer's ownership definition, while hook trust inspects the owned config.toml. Config vetting alone cannot exclude account-installed plugins: the supplied upstream rust-v0.162.1 review identifies plugins as enabled by default in features/src/lib.rs:1559, startup downloads in app-server/src/in_process.rs:517, config-independent bundled hook loading in manager.rs:995-1011 and loader.rs:341, bypass application in discovery.rs:286, and per-turn reloads in plugin_selection.rs:24. Invocation-level plugin disabling covers that source as well. These are supplied source references, without an independent upstream execution or canary claim.
